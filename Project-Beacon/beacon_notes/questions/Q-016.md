# Q-016 Quality attributes BEACON must meet

## What is unknown

For each quality attribute in the checklist below, what measurable level must BEACON meet, and must it be settled before the first component is entered, or can it be settled during that component's decomposition? Prompt injection ([[Q-017]]) and privacy ([[Q-018]]) have questions of their own.

B = settle before the first component is entered. D = settle during the decomposition of the component it bears on.

## Why this priority

P1: architecture is about to start, and these attributes shape its choices (hosting region, stores, model provider, fetcher). Component work can proceed under the assumptions above, so it is not P0; it is not P2, because several assumptions (region, cost ceilings, secrets) are expensive to reverse once built.

## Answered when

Every checklist item carries either a measurable target (a number, a standard and a level, or a named region) with its verification, or an explicit "not required", each approved by the owner; the items marked B are answered before the first component is entered.

## If it stays unknown

BEACON is built to the assumption column. Each component records which assumptions it relied on, so that an answer changes targets, not structure.

## Evidence so far

Measured on one laptop on 2026-09-28 ([[X-001]], [[X-002]]): a run over ten sources kept about 176 items in 15.7 minutes, and a pass over 226 sampled items took about 24 minutes. Crawl delays that sites ask in robots.txt, 15 seconds on the slowest, set the pace rather than the fetching itself. A local 8-billion-parameter model on an 8 GB GPU read a page's metadata in about 1.4 seconds once loaded (18 seconds cold); a local vision model read a scanned page in about 2 minutes at the resolution that transcribed it faithfully.
